# Безопасность tenge.gg: что реализовано и что нет

Документ описывает фактическое состояние, а не намерения. Каждый пункт помечен честно:
**реализовано**, **частично** или **не реализовано**. Ссылки — на конкретные файлы.

## Модель угроз (по убыванию ущерба)

| # | Угроза | Последствие | Статус защиты |
|---|---|---|---|
| 1 | Сделка уходит мимо escrow (контакты и реквизиты в чате) | вернуть деньги нечем, арбитраж невозможен | реализовано |
| 2 | Подделка вебхука оплаты | «оплата» без денег, вывод средств | реализовано |
| 3 | Гонка на переходах сделки (двойная выплата) | двойной расход escrow | реализовано |
| 4 | Повторная доставка вебхука / двойной заказ | двойное списание или выплата | реализовано |
| 5 | Доступ к чужой сделке (IDOR) | утечка переписки и данных товара | реализовано (RLS) |
| 6 | Угон сессии, вывод после смены пароля | кража баланса | **не реализовано** (нет 2FA и hold) |
| 7 | Мультиаккаунт и накрутка отзывов | подрыв доверия к рейтингу | частично |
| 8 | Флуд / брутфорс / DoS на мутациях | недоступность, спам | частично |

## Что реализовано

### Целостность денег и состояний
- **Escrow как стейт-машина.** Переходы разрешены только по графу `TRANSITIONS`
  (`src/lib/escrow/state-machine.ts`), тот же граф продублирован в БД. UI не показывает
  действие, которое сервер отклонит, но решает всегда сервер.
- **Блокировки.** Строка заказа берётся `SELECT ... FOR UPDATE` внутри RPC
  (`supabase/migrations/20260802120100_escrow_state_machine_core.sql`), плюс optimistic
  locking по `orders.version` (`p_expected_version`). Спор блокирует вывод денег даже
  при параллельных запросах.
- **Идемпотентность в три уровня** (`src/services/escrow.service.ts`):
  `UNIQUE(provider, event_id)` в `payment_webhooks`, проверка статуса под блокировкой,
  `UNIQUE(idempotency_key)` и частичный `UNIQUE(order_id)` в `transactions`.
  Повторная доставка вебхука всегда возвращает `ok=true` — Kaspi не уходит в retry-шторм.
- **Никаких ручных статусов.** Панель `/admin` работает со сделками только на чтение;
  единственный путь изменения — escrow-переходы и `/arbitration`.

### Вебхук оплаты
- HMAC-SHA256 от `${timestamp}.${rawBody}`, сравнение через `crypto.timingSafeEqual`,
  окно защиты от replay 300 секунд (`src/lib/kaspi/signature.ts`).
- Схема payload проверяется zod до обращения к БД (`src/lib/kaspi/webhook.schema.ts`).
- Несовпадение суммы фиксируется как `REJECTED` и не двигает деньги.

### Доступ
- RLS на всех пользовательских таблицах; роль решает `is_staff()` / `is_arbiter()` в БД —
  та же функция, что в политиках, а не флаг в браузере.
- `service_role` ключ используется только в вебхуке и cron (`import 'server-only'`),
  в клиентские бандлы не попадает.
- Приватные маршруты закрыты в `middleware.ts`, сессия обновляется на edge.

### Анти-байпас платформы (`src/lib/security/`)
- `contact-leak.ts` — сканер переписки и объявлений:
  - **блокирует** номера карт (regex + проверка Luhn, чтобы игровой ID не считался картой)
    и счета `KZ...` — такой текст не попадает в БД вообще;
  - **маскирует** телефоны, `@хендлы`, `t.me`, e-mail, внешние ссылки (свой домен не трогает);
  - ловит намерение «мимо сайта» по фразам, устойчиво к разделителям («т.е.л.е.г.р.а.м»),
    гомоглифам («tелеgram») и leet;
  - «Kaspi» сам по себе нарушением не считается — это платёжный метод платформы.
- `text.ts` — нормализация NFKC, удаление zero-width и управляющих символов до валидации,
  иначе лимиты длины обходятся невидимыми символами.
- `rate-limit.ts` — лимиты частоты на чат, публикацию лота, отзывы, профиль.
- Проверки применяются **на сервере** в Server Actions; клиент только показывает результат.
- Регрессия закрыта тестом: `npm run test:security` (14 кейсов, включая обходы и ложные срабатывания).

### Почему Postgres, а не Redis
Лимиты и идемпотентность живут в той же БД и в той же транзакции, что и данные. Redis дал бы
отдельную точку отказа и окно рассинхрона между «лимит списан» и «операция применена».
При росте нагрузки лимитер выносится в Redis без изменения вызывающего кода — интерфейс
`enforceRateLimit` этого не заметит.

### Почему нет DOMPurify
Пользовательский текст рендерится React как текстовый узел, `dangerouslySetInnerHTML` в проекте
не используется, CSP запрещает внешние скрипты (`next.config.ts`). Санитайзер HTML нужен только
там, где HTML рендерится осознанно; такого места нет. Добавлять его «на всякий случай» —
ложное чувство защиты.

## Что не реализовано (осознанные пробелы)

| Требование | Почему не сделано сейчас | Что нужно |
|---|---|---|
| 2FA (TOTP / Telegram OTP) на выплаты и смену пароля | нет модуля выплат, защищать пока нечего | `user_mfa` + проверка в payout-action |
| Rolling payout hold 24–48 ч для новых продавцов | требует таблицы выплат и баланса | `payouts` + `sellers.trust_tier` |
| Автовыдача цифровых товаров | нужен шифрованный vault и ключи KMS | `delivery_items` + AES-GCM на ключе вне БД |
| Device fingerprint, детект мультиаккаунтов | нет сбора сигналов | таблица `auth_signals` + скоринг |
| KYC-уровни и верификация телефона | внешний провайдер не подключён | tiers + провайдер верификации |
| Cloudflare Turnstile / WAF | не подключён домен | проверка токена в auth-actions |
| Загрузка доказательств в спор из UI | bucket `evidence` есть, интерфейса нет | форма в комнате сделки |
| Персистентный `security_events` | миграция написана, но не применена | `npm run db:push && npm run db:types` |

## Порядок применения миграции журнала

```bash
npm run db:push    # применяет supabase/migrations/20260803210000_security_events.sql
npm run db:types   # регенерирует src/types/database.types.ts
```

До этого `logSecurityEvent` пишет структурированный JSON в stdout: платформа деплоя собирает
логи без дополнительной инфраструктуры. Код сознательно не обращается к таблице, которой ещё
нет, — иначе чат падал бы на каждом срабатывании фильтра.

## Правила, которые нельзя нарушать при доработках

1. Любая проверка прав — на сервере и в БД. Скрытая кнопка не является защитой.
2. Деньги двигаются только через escrow-RPC. Прямой `update` статуса заказа запрещён.
3. Все финансовые операции идемпотентны по ключу от клиента.
4. Секреты не попадают в клиентские компоненты: файл с секретом начинается с `import 'server-only'`.
5. В логи не пишутся сами реквизиты — только вид находки.
6. Новый фильтр или лимит сопровождается кейсом в `scripts/security.selftest.mjs`.
